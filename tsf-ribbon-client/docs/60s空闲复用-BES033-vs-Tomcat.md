# BES 9.5.5.033 与 Tomcat 空闲连接 60 秒关闭复用问题验证报告

| 项 | 内容 |
|---|---|
| 验证目标 | 模拟并验证"服务端 KeepAliveTimeout=60s 关闭空闲连接后，客户端继续复用该连接导致调用报错（Unexpected end of file from server）"的场景，并对比 BES 与 Tomcat 的行为 |
| 验证日期 | 2026-09-15 |
| 客户端 JDK | 毕昇 BiSheng JDK 1.8.0_452（与生产环境一致） |
| 服务端引擎 | BES-AppServer-SpringBoot-2.x 9.5.5.033（嵌入式 lite-starter）与 Spring Boot 2.7.18 内嵌 Tomcat 9.0.108，均使用默认连接器配置 |
| 结论速览 | 该场景**真实存在且已在两种引擎上复现**：触发条件是"客户端到服务端的网络往返延迟 + 请求写耗时超过服务端关闭动作的迟滞量（实测约 56~391ms）"；同机房快链路上结构性不发生，跨网段（广域网）访问时偶发命中——与现场"偶发、可自愈"的报错形态吻合。两种引擎行为等价。 |

## 1. 测试环境

### 1.1 机器与角色

| 角色 | 机器 | 部署内容 |
|---|---|---|
| 服务端机器 | 192.168.56.109（Linux） | 同机部署两组服务端实例：Tomcat 引擎实例（端口 18091）、BES 引擎实例（端口 18191），运行同一 REST 测试应用，均保持引擎默认配置（KeepAliveTimeout=60s、maxKeepAliveRequests=100/1024） |
| 客户端机器 | 192.168.56.108（Linux） | 同机部署两组客户端实例：对接 Tomcat 的客户端（端口 18093）、对接 BES 的客户端（端口 18193），各自只配置一个服务端地址（隔离引擎、保证调用可预测） |

两台机器之间为千兆直连网络（内网往返约 1ms），作为"同机房快链路"基线；需要模拟跨网段/广域网时，在客户端机器出口方向对发往服务端机器的流量注入单向固定延迟（100ms / 150ms，使用 Linux 流量控制 netem，只影响测试流量、按目标地址过滤），其余方向不受影响。

### 1.2 客户端调用栈（与生产一致）

客户端应用通过 Spring Cloud LoadBalancer（@LoadBalanced RestTemplate）调用服务端 REST 接口，底层为 JDK HttpURLConnection（SimpleClientHttpRequestFactory），并启用 spring-retry 重试拦截器。完整调用链为：

```
RestTemplate.postForEntity → RetryLoadBalancerInterceptor → RetryTemplate
→ TsfBlockingLoadBalancerClient → SimpleClientHttpResponse → HttpURLConnection
```

与生产应用报错时的调用栈一致，报错可逐帧对应。

### 1.3 测试应用

服务端提供 REST 回显接口（POST，JSON 报文），支持以下参数：
- `sleepMs`：模拟业务处理耗时；
- `respSize`：响应报文字节数（Content-Length 精确，非 chunked）。

客户端提供以下测试入口：
- **空闲复用专项**：每轮执行"预热调用（建立/复用连接）→ 按指定时长精确空闲（毫秒级）→ 探测调用 → 恢复调用"，记录每步的状态码、耗时、异常（含完整调用栈），并在调用前后读取 JDK 连接缓存的内部状态（缓存保留时长 nap、空闲时长、连接本地端口），用于判定连接是复用还是新建；
- **通用流程**：预热 → 空闲 → 多次探测 → 恢复；
- **缓存状态查看**：实时显示当前 JVM 连接缓存的 nap 值与连接列表。

报文大小、空闲时长、探测次数均通过 URL 参数调整，支持按毫秒级间隔逐轮扫描空闲时长。

## 2. 机制说明

### 2.1 客户端连接缓存时长由服务端决定

对毕昇 JDK 1.8.0_452 的 HttpURLConnection（反编译核实 + 运行时反射实测）：

- 客户端会把空闲连接放入缓存，**缓存保留时长（nap）优先采用服务端响应头 `Keep-Alive: timeout=N` 的值**；
- 只有服务端不返回该头时，才使用本地系统属性（默认 5 秒）；
- BES 9.5.5.033 与 Tomcat 9.0.108 默认都会返回 `Keep-Alive: timeout=60`，因此客户端会把空闲连接持有满 **60 秒**，与服务端的 KeepAliveTimeout=60s **精确对齐**——空闲约 60 秒的调用方是最危险的复用者；
- 缓存计时起点是"客户端读完响应体的时刻"，复用判定为"空闲时长 ≤ 60s 才复用，超过即新建连接"。

### 2.2 服务端关闭时机

两种引擎在默认配置下的实测行为：

| 行为 | Tomcat 9.0.108 | BES 9.5.5.033 |
|---|---|---|
| 空闲关闭时刻（实测服务端 FIN 相对客户端读完响应） | +60.06s 左右（样本 +60.07~+60.20s） | +60.06s 左右（样本 +60.09~+60.39s） |
| keep-alive 计时器起算点 | **响应写完**（业务耗时 0.5/2/10 秒均不改变关闭时刻） | 同左 |
| KeepAliveTimeout 显式调整时响应头是否跟随 | 跟随（如设为 30s → 头变为 timeout=30） | 跟随（同左） |

要点：
1. 关闭时刻恒为"响应写完 + 60s + **λ**"，λ 是引擎内部的轮询迟滞，实测 +56~+391ms，**恒为正、逐次抖动**；
2. 计时器从响应写完起算——**业务处理慢（哪怕 10 秒）不会让服务端提前关闭连接**；
3. 引擎广播给客户端的超时值与实际关闭行为一致，不存在"广播 60 实际更早关"的脱钩。

### 2.3 错误窗口

设 λ=服务端关闭迟滞（+56~391ms）、D1=请求方向网络延迟、D2=响应方向网络延迟、w=请求报文写耗时、φ=客户端内部派发开销、K=KeepAliveTimeout（客户端缓存时长恒等于 K）：

```
客户端会复用缓存连接：      空闲时长 ≤ K − φ
复用时服务端已关闭：        空闲时长 > K + λ − D2 − φ − w − D1

错误窗口 = (K + λ − D2 − φ − w − D1,  K − φ]，非空条件：D1 + D2 + w > λ
```

- **同机房快链路**：D1+D2+w ≈ 2ms，远小于 λ（≥56ms）→ 窗口为空，默认配置下结构性不会发生此错误；
- **跨网段/广域网**：网络往返延迟（D1+D2）达到百毫秒级，远超 λ → 窗口宽度约等于"往返延迟 − λ"，几十至上百毫秒；空闲时长落在窗口内的调用就会报错；
- 服务端的 FIN 恒晚于客户端缓存过期 → 窗口内客户端先读到 FIN（EOF）→ 错误形态必然是 **"Unexpected end of file from server"**（个别时序下为 Connection reset），与现场报错一致；
- λ 逐次抖动 → 窗口边界逐次漂移 → 是否命中呈概率性，这就是"偶发"的来源。

## 3. 测试场景与结果

### 3.1 同机房快链路基线（无人工延迟）

空闲时长扫描 59.9~60.0 秒（毫秒级间隔）× 报文 1KB/512KB × 两种引擎：**全部成功、0 错误**。抓包证实空闲 59.999 秒的探测确实复用了原连接且服务端尚未关闭。
→ 快链路上该场景不发生。

### 3.2 KeepAliveTimeout 显式调整的核对

将引擎 KeepAliveTimeout 显式设为 30 秒，实测两种引擎的响应头均跟随变为 `timeout=30`，客户端缓存时长同步变为 30 秒——广播值与实际行为一致，客户端与服务端始终对齐。

### 3.3 模拟广域网（请求方向注入 100ms 延迟，默认 K=60）

空闲时长扫描（60.0 → 59.9 秒递减，10 档）：

| 引擎 | 命中情况 | 错误形态 |
|---|---|---|
| Tomcat 9.0.108 | 空闲 59.980 秒时报错 | Unexpected end of file from server |
| BES 9.5.5.033 | 空闲 59.960 秒时报错 | Connection reset |

相邻档位成功、单点命中，是 λ 抖动的直接体现（该轮次窗口宽度约 10~45ms）。

### 3.4 完整调用栈统计复现（请求方向注入 150ms 延迟，默认 K=60）

通过客户端应用的负载均衡全栈（与生产一致的调用链）执行统计轮，每引擎 6 轮（空闲时长 59.988~59.968 秒）：

| 引擎 | 报错数/探测数 | 错误形态 |
|---|---|---|
| Tomcat 9.0.108 | **4/6** | 全部 Unexpected end of file from server |
| BES 9.5.5.033 | **5/6** | 全部 Unexpected end of file from server |

BES 侧捕获的完整异常栈与生产报错**逐帧一致**（HttpClient.parseHTTPHeader → SimpleClientHttpResponse → TsfBlockingLoadBalancerClient → RetryLoadBalancerInterceptor → RestTemplate，各层行号均相同）。

每轮流程中，探测调用报错后**紧跟的恢复调用立即成功**（客户端自动新建连接，无需人工干预）——与现场"报错后下一笔正常"的自愈形态一致。

### 3.5 缓解措施验证（开启负载均衡自动重试）

同一条件（150ms 延迟、同样的空闲时长档位）下，将客户端负载均衡重试配置 `retry-on-all-operations` 设为 true 后重跑 4 轮：**4/4 全部成功**，单次调用耗时 336~512ms（≈ 失败首试 + 新连接重试的时间特征）——自动重试可完全掩盖此类错误。

## 4. BES 与 Tomcat 对比结论

| 维度 | 结论 |
|---|---|
| 60 秒空闲关闭语义 | **等价**：均从响应写完起算，均带 +λ 迟滞关闭（Tomcat λ ≈ 56~195ms，BES λ ≈ 64~391ms，BES 略晚且抖动稍大） |
| Keep-Alive 响应头 | **等价**：默认 timeout=60，显式调整时均跟随 |
| 窗口内错误形态 | **等价**：均以 Unexpected end of file from server 为主（BES 出现过一次 Connection reset，属 FIN/RST 到达时序差异，非引擎缺陷） |
| 复现率（150ms 延迟，各 6 轮） | Tomcat 4/6、BES 5/6，同量级 |
| **总体** | **该场景下两种引擎行为等价，引擎选择本身不改变此错误的发生条件** |

## 5. 对生产环境的分析

1. 生产中客户端跨网段访问服务端（如访问 214.9.245.119），网络往返延迟加上请求写耗时若超过服务端关闭迟滞量（几十毫秒），错误窗口即真实存在；
2. 周期约 60 秒的定时调用（如消息转发/账户同步类任务），其调用点会随机落入 60 秒前的最后几十毫秒窗口内 → **偶发** "Unexpected end of file from server"；
3. 若生产曾使用"空闲连接永不关闭"的旧版本配置/旧版本包，则旧环境下该窗口不存在（服务端不关闭，客户端复用永远成功）；升级到会按 60 秒关闭的版本后，窗口从无到有，错误从 0 变为偶发——**这与引擎是 BES 还是 Tomcat 无关，取决于"是否开始关闭空闲连接"这一行为变化**；
4. 备选/叠加因素（实验室无法复现，需生产数据裁决）：中间网络设备（负载均衡/防火墙）更早回收空闲会话（错误形态相同）；服务端发布重启（错误形态为成簇 + 连接拒绝，与现场偶发形态不符，基本可排除）。

## 6. 生产环境排查建议

| # | 动作 | 判读 |
|---|---|---|
| 1 | `curl -sv -H "Connection: keep-alive" http://<服务端地址>:<端口>/ 2>&1 \| grep -i keep-alive` | 返回 `Keep-Alive: timeout=60` 即表示客户端（毕昇 JDK 1.8.0_452）会把空闲连接持有满 60 秒，60 秒间隔的调用方处于复用窗口上沿 |
| 2 | 统计客户端日志中报错请求与前一成功请求的间隔分布 | 聚集在约 59.9~60.0 秒（最后几十毫秒）→ 本机制坐实；聚集在其它值 → 查中间设备或重启 |
| 3 | 实测客户端到服务端的网络往返延迟（ping 或 curl time_total） | 往返延迟 + 请求耗时超过约 60ms（迟滞量级）→ 窗口打开；明显小于 → 纯内网场景下本机制不成立，需排查其它断链来源 |
| 4 | 确认服务端实际生效的 keep-alive-timeout 配置，及升级前旧版本的该配置 | 若旧版本为"永不关闭"，升级后错误从无到有即本机制，且与引擎无关 |
| 5 | 报错时间分布与服务端发布/重启时间轴比对 | 不相关 → 排除发布重启因素 |

## 7. 缓解建议（按优先级）

| 方案 | 效果 | 代价/风险 |
|---|---|---|
| 客户端开启负载均衡自动重试（`retry-on-all-operations=true`，实测 4/4 掩盖） | 失败自动换连接重试，业务无感 | POST 非幂等场景需评估重复投递；重试多耗一次往返延迟 |
| 客户端关闭连接复用（`-Dhttp.keepAlive=false`） | 不复用连接，窗口消失 | 每次调用新建 TCP 连接，高频调用下开销上升 |
| 服务端调大 keep-alive-timeout（如 300 秒，大于最大调用间隔） | 服务端不再在调用间隔内关闭连接 | 占用服务端连接资源，需评估并发连接数 |
| 调用方避开 60 秒整周期（错峰/加随机抖动） | 降低落入毫秒级窗口的概率 | 不彻底 |

## 8. 附：验证方法说明

- 服务端关闭时机：使用原生 TCP 连接发送请求、读取响应后阻塞等待服务端 FIN/RST，以毫秒精度记录关闭时刻（避免任何轮询方式的时间误差）；
- 全程在服务端机器抓包（tcpdump），与客户端/服务端日志时间戳三方互证；
- 客户端连接缓存内部状态（缓存时长、空闲计时、连接端口）通过运行时反射直接读取，用于判定每次调用是"复用"还是"新建"；
- 空闲时长控制精确到毫秒（粗睡 + 细睡 + 自旋对齐）；
- 所有测试在引擎默认配置下进行，显式调整配置的场景已注明。
