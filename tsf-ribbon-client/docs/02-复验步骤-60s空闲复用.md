# 60s 空闲复用场景复验步骤（BES 9.5.5.033 vs Tomcat 9.0.108）

> 供第三方独立复验《60s空闲复用-BES033-vs-Tomcat.md》。按顺序执行即可复现；
> 每个场景给出**预期结果**与**本报告实测值**，复验后填入对照表（文末）。

## 0. 场景一句话

服务端 KeepAliveTimeout=60s 关闭空闲连接（关闭动作带 +λ 迟滞，λ≈56~391ms 恒正），
毕昇 JDK 1.8.0_452 客户端的连接缓存 nap 又恰好=60s（跟随服务端 `Keep-Alive: timeout=60` 头）——
当"网络往返延迟 + 请求写耗时 > λ"（即跨网段/广域网）时，空闲 60s 附近的调用存在毫秒级
错误窗口，复用已死连接报 **`Unexpected end of file from server`**；同机房快链路（RTT~1ms）
结构性不发生。

## 2. 部署与启动

产物打包见《01-应用打包步骤.md》；**成品 jar、license、启停脚本已收集在本目录 `packages/`**（从验证机取回，附 MD5 清单，部署后先核对 md5）。两台机器部署目录内已含同款 start/stop 脚本与 license。

### 2.1 启动服务端（109）

```bash
ssh user@192.168.56.109
cd ~/MiddleWare/bessystem/SpringBoot/Ribbon
./start-server.sh tomcat 18091
./start-server.sh bes 18191
# 查看日志确认就绪（Tomcat 侧应有 "Tomcat started on port(s): 18091"；BES 侧日志无 license 报错）
tail -5 server-18091.log server-18191.log
```

### 2.2 启动客户端（108）

```bash
ssh bes@192.168.56.108
cd ~/MiddleWare/bessystem/SpringBoot/Ribbon
./start-client.sh tomcat --spring.cloud.discovery.client.simple.instances.tsf-ribbon-server[0].uri=http://192.168.56.109:18091
./start-client.sh bes    --spring.cloud.discovery.client.simple.instances.tsf-ribbon-server[0].uri=http://192.168.56.109:18191
tail -5 client-tomcat-18093.log client-bes-18193.log
```

> 启动参数覆盖了 yml 里的 localhost 默认实例列表——LB 列表只指向对应引擎的单实例，
> 保证调用路径可预测。**重启客户端前必须先存档日志**（脚本用 `>` 覆盖，见第 8 节踩坑）。

### 2.3 停止

```bash
# 109
./stop-server.sh 18091 && ./stop-server.sh 18191
# 108
./stop-client.sh    # 需要时按 PID 文件 client-tomcat.pid / client-bes.pid 精确 kill
```

## 4. netem 注入与清理（108，root）

只延迟"发往 109 的流量"，对管理 ssh 等其它方向无影响（108 上的会话不受影响）：

```bash
ssh root@192.168.56.108    # 密码 password

# 0) 清残留（每个场景开始前必做，防止上次规则污染）
tc qdisc del dev enp0s3 root 2>/dev/null; tc qdisc show dev enp0s3

# 1) prio 根 + netem 挂 band 4
tc qdisc add dev enp0s3 root handle 1: prio bands 4
tc qdisc add dev enp0s3 parent 1:4 handle 40: netem delay 150ms   # 100ms 场景改为 100ms

# 2) 只把 dst=109 的流量导入 band 4
tc filter add dev enp0s3 protocol ip parent 1:0 prio 4 u32 match ip dst 192.168.56.109 flowid 1:4

# 3) 确认
tc qdisc show dev enp0s3

# 4) 场景结束必须删（否则污染后续所有场景）
tc qdisc del dev enp0s3 root
```

## 5. 复验场景（按序）

测试入口都在客户端 `IdleReuseServlet`：每轮 **预热 →（毫秒级精确）空闲 gap → 探测 → 恢复**，
输出每步状态码/耗时/异常与调用前后 KeepAliveCache 快照（本地端口不变=复用，变=新建）。

### 场景 V1：快内网基线（无 netem）——预期 0 错误

不注入任何延迟。对两组各执行 gap 扫描（gapList 从 60s 往下扫）：

```
http://192.168.56.108:18093/IdleReuseServlet?size=1024&gapList=60000,59999,59997,59995,59990,59980,59950,59900
http://192.168.56.108:18193/IdleReuseServlet?size=1024&gapList=60000,59999,59997,59995,59990,59980,59950,59900
# 可再加 size=524288（512KB）验证大报文
```

**预期：全部 200 成功、0 报错**（快链路 RTT+写耗时 ~2ms < λ≥56ms，错误窗口为空）。
本报告实测：0 错误（sweepT.log / sweepB.log，evidence/）。

### 场景 E3：模拟广域网 100ms——预期单点命中

108 注入 `netem delay 100ms` 后，两组各扫 5 档：

```
http://192.168.56.108:18093/IdleReuseServlet?size=1024&gapList=59980,59975,59970,59965,59960
http://192.168.56.108:18193/IdleReuseServlet?size=1024&gapList=59980,59975,59970,59965,59960
```

**预期：恰在某 1 档报错、相邻档成功**（λ 抖动导致窗口边界漂移）。

本报告实测：

| 引擎 | 命中档位 | 错误形态 |
|---|---|---|
| Tomcat 9.0.108 | 59.980s | Unexpected end of file from server |
| BES 9.5.5.033 | 59.960s | Connection reset（FIN/RST 到达时序差异，非引擎缺陷） |

### 场景 E4：150ms 完整调用栈统计——预期 4~6/6 报错且栈与现场一致

注入 `netem delay 150ms` 后，两组各跑 6 轮：

```
http://192.168.56.108:18093/IdleReuseServlet?size=1024&gapList=59988,59984,59980,59976,59972,59968
http://192.168.56.108:18193/IdleReuseServlet?size=1024&gapList=59988,59984,59980,59976,59972,59968
```

**预期/核对点**：
1. 每组 **4~6 轮报错**，形态以 `Unexpected end of file from server` 为主；
2. 客户端日志（`client-*-18093/18193.log`）中完整栈逐帧对照现场：
   `HttpClient.parseHTTPHeader → SimpleClientHttpResponse.getRawStatusCode → TsfBlockingLoadBalancerClient.executeInternal → RetryLoadBalancerInterceptor.lambda$intercept$2 → RetryTemplate → RestTemplate`（evidence/E3-完整调用栈-BES-默认K60-150ms延迟.md 可直接比对）；
3. 每轮探测报错后**紧跟的"恢复"调用立即成功**（新建连接，自愈）——与现场"报错后下一笔正常"吻合。

本报告实测：Tomcat 4/6、BES 5/6，全部 Unexpected end of file from server。

### 场景 E5：缓解措施——开启自动重试后预期 0 报错

保持 150ms 延迟。**重启客户端并开启重试**（先存档日志！）：

```bash
# 108（Tomcat 组为例；BES 组同理）
cp client-tomcat-18093.log client-tomcat-18093.log.prev    # 必须先存档
./stop-client.sh
./start-client.sh tomcat \
  --spring.cloud.discovery.client.simple.instances.tsf-ribbon-server[0].uri=http://192.168.56.109:18091 \
  --spring.cloud.loadbalancer.retry.retry-on-all-operations=true
```

同样的 gap 档位重跑 4 轮（`gapList=59984,59980,59976,59972`）。

**预期：4/4 全部成功**，单次耗时 ~336~512ms（失败首试 + 新连接重试的时间特征）。
本报告实测：4/4 成功（E4-tomcat-retry-enabled-150ms.html）。

## 8. 踩坑与操作纪律（前车之鉴，务必遵守）

1. **`pkill -f tsf-ribbon-server` 会自杀**：模式匹配到 ssh 会话自身命令行，exit 255。一律用 `../../tsf-ribbon-server/stop-server.sh`/`../stop-client.sh` 或按 PID 文件 kill。
2. **start 脚本用 `>` 覆盖日志**：重启客户端/服务端前必须 `cp` 存档，否则日志丢失（E3 的 tomcat 栈因此丢过一次，靠 HTML+pcap 补救）。
3. **ss 假阴性**：Java Runtime.exec 里 `ss` 不在 PATH（在 `/usr/sbin/ss`），且轮询偶发漏连接；关键计时用裸 socket 阻塞 read() 等服务端 FIN（RawFinTest 的做法），不要用 ss 轮询下结论。
4. **netem 残留**：每个场景开始前 `tc qdisc del dev enp0s3 root`，结束后再删并 `tc qdisc show` 确认。
5. **BES license**：文件必须叫 `bes.lic.txt`；EVALUATE 到 2026-12-31，过期起不来。
6. **BES 配置单位**：`server.bes.keep-alive-timeout` 是**秒**（Integer），写 `5s` 启动失败。
7. **默认 K 不要动**：所有对比场景在引擎默认配置（60s）下进行，显式改配置的场景已注明。
